# Vibez & Butterflyz — Sensory & Mood Studio — Rebuild Prompt

Build a single-page web app (static HTML/CSS/JS, no framework or build step required) called **Vibez & Butterflyz Sensory & Mood Studio**: an essential-oil blending tool wrapped in an immersive, guided, "butterfly-lit studio" experience. Everything below is implementation-agnostic — build it in any stack, but preserve the behavior and constraints as written.

## Visual system

- **Palette**: deep indigo-black background (`#0F0B1A`), warm off-white primary text, soft amethyst violet as the primary accent (`#9D7FD4`), warm amber gold as the secondary accent (`#C9A85C`), a dusty rose for warnings/highlights. Gradients combine rose→violet or gold glows against the dark background. No light theme.
- **Typography**: a serif display face (headings, card titles) paired with a clean sans-serif for UI text.
- **Signature motif**: one piece of butterfly artwork (deep purple/violet wings, gold trim, transparent background) used everywhere — sidebar logo, guide/tour emblems, onboarding icon, mood-quiz tiles, card decoration. Use **one** real image asset embedded directly in the page (e.g. as a base64 data URI) rather than a separate file — static builds get shared/opened standalone often enough that a second file *will* go missing. Do not hand-draw a vector approximation; use real artwork.
- **Cards**: oil cards are butterfly-shaped, flip on click (front: name/note/quick actions; back: safety/key notes/pairing), with a subtle "gold dust" sparkle treatment. Provide at least two density/layout options (grid and a horizontal-scroll carousel) with a small switcher control.
- **Accessibility floor**: every text color against its background must meet WCAG AA (4.5:1 for normal text, 3:1 for large/bold text ≥18px). Every interactive control needs a visible focus state (never remove `outline` without substituting a real focus indicator). Every icon-only button needs an accessible name (`aria-label` or equivalent).

## Core data

- **Oil library**: each oil has a name, botanical (Latin) name, category, fragrance note (Top/Middle/Base), aroma descriptor tags, chemical constituents (name + percentage) *where real data exists*, a phototoxicity flag, a numeric max-dermal-dilution percentage *where a real source gives one*, cautions, pregnancy guidance, and "pairs with" / "traditional uses" lists.
  - **Never fabricate safety numbers.** If a source doesn't give a specific dermal limit or chemical breakdown for an oil, leave it out and have the UI say so plainly ("data pending") rather than inventing a precise-looking figure. The safety/dilution calculator is only as trustworthy as its worst silent guess.
- **Curated blend library**: pre-built blends grouped by mood/category, each with its own oils+ratios, a diffuser recipe, a topical recipe, a wearability note, and a **unique** affirmation. If your affirmations share a common opening template per category, don't let a card's teaser truncate to just that shared opening sentence — it'll read as if every card has the same one or two affirmations even though the full text differs. Show something guaranteed-unique instead (e.g. the blend's own recipe line).

## Flow, in order

1. **Email gate** (optional but if present, must be real): a full-screen, unskippable panel requiring an email before anything else loads. Validate format client-side; submit to a real form backend (e.g. Formspree) via `fetch` with proper error handling — a failed submission must show an error and *not* unlock the site. If the backend isn't configured yet, fail open with a visible on-screen dev notice rather than silently locking out every visitor forever. Remember a successful pass (e.g. `localStorage`) so returning visitors aren't asked again — but don't auto-focus the input, since focusing an element inside a fixed-position overlay on load makes mobile browsers scroll the whole document trying to "help," which visibly opens the page pre-scrolled.
2. **Welcome**: a short, dismissible greeting ("What kind of mood would you like to set today?").
3. **Mood quiz**: a grid of mood tiles (icon + label + one-line description), each mapped to a starter blend. Icons must be large enough to actually read at a glance (≥36px), not decorative specks.
4. **Guided walkthrough**: an auto-starting, step-by-step tour (progress dots, back/next, step count) that teaches each tab in order, tailored to the mood just picked. Must be:
   - **Draggable and collapsible** — never permanently blocks content.
   - **Compact and translucent by default**, not just on one screen-size tier: cap it by an absolute pixel height as well as a viewport-relative one (e.g. `min(34vh, 320px)`), and keep the same sizing/opacity rules regardless of exact device width — don't gate the "small" version behind a single CSS breakpoint guess, since real devices report a wider range of viewport widths than you'll think to test.
   - Every dismiss path matters: a labeled "Skip" button is a deliberate opt-out (remember it permanently); an incidental tap on the backdrop or a bare ✕ is *not* deliberate and should only dismiss for that pageview, not silently disable the walkthrough forever on that device.
5. **Always-available Tour**: a small corner button (independent of the onboarding walkthrough) that replays the same guided-step mechanism in a "tour" mode, for anyone who skipped onboarding or wants a refresher. Never auto-opens.
6. **Main app**, tabbed:
   - **Oil Library**: search, filter (true EO vs. fragrance, note, category, phototoxicity), butterfly-card grid/carousel, tap to flip for safety info, add to active blend.
   - **Blend Analyzer**: live note-balance (top/middle/base %), full safety assessment (phototoxicity + pregnancy + per-oil cautions, driven by the *most restrictive* oil in the blend), chemical composition breakdown, aggregated therapeutic actions, and a dilution-ready recipe calculator (drops per volume at a chosen use-case dilution %).
   - **Terpenes**: reference library of aroma constituents with their therapeutic actions and source oils.
   - **Curated Moods**: browse the pre-built blend library, filterable by mood/category, load one straight into the active blend.
   - **Moodlab**: turn the active blend into a downloadable "Mood Card" (title, tagline, affirmation, oil chips, PNG export) — and directly alongside it, **the Lounge Experience**: a wine/cocktail/mocktail/small-plate pairing inferred from the blend's dominant mood. Keep these two together; the pairing feature reads as disconnected filler if it's off in a different tab from the blend it's supposedly reacting to.

## Cross-cutting behavior rules (learned the hard way — keep these)

- **A visible UI element must actually update.** If a feature's data-computation function only gets called from one specific view's render path, and you later move that feature's markup into a different view, the function call has to move with it (or be called from both). Test this explicitly: pick a mood, confirm the pairing/dependent UI actually changes, not just that the DOM exists.
- **Name matching for any oil/mood inference logic must handle qualified names.** Real oil libraries have chemotype/varietal suffixes ("Chamomile (Roman)", "Rosemary (ct. Cineole)", "Eucalyptus Globulus"). Exact-string keyword matching against a bare "chamomile"/"rosemary" will silently fail for most of your real inventory. Strip parenthetical qualifiers and fall back to a word-boundary prefix match.
- **`localStorage` (or any persistence API) can throw, not just return empty.** Some sandboxed/secure viewers throw a `SecurityError` the instant it's touched, not just when full or disabled gracefully. Wrap every read/write in a try/catch that degrades to "nothing was stored" — an uncaught throw early in a page's script halts everything after it, which can silently blank an entire feature (e.g. a whole library rendering as zero items) for a reason that has nothing to do with the feature itself.
- **`100vh` is a trap on mobile.** It includes space hidden behind a collapsible browser address bar, so a modal/panel sized off `vh` can render taller than what's actually visible even though the CSS looks correct. Pair every `vh`-based `max-height`/`min-height` with a `dvh` override declared immediately after it (unsupported browsers ignore the unrecognized value and keep the `vh` fallback automatically).
- **Auto-scrolling an element into view is not free.** If you add `scrollIntoView` logic to keep some UI clear of a fixed overlay, make sure it can't fire during the page's very first automatic render (before any user interaction) — that scrolls the page out from under whatever gate/overlay is currently covering it, so the app "opens in the middle" the moment that overlay is dismissed. Only trigger it from genuine user actions (a tab click), not an unconditional render call.
- **Fixed-position corner UI (a floating help button, a minimized panel pill, etc.) will eventually sit on top of normal-flow content** as the page scrolls, unless the scrollable container reserves real bottom padding for it. A mobile breakpoint that collapses padding down to a flat, small value for *all* sides will usually eat that reserved space — check the bottom specifically, not just left/right.
- **A component sized with a fixed pixel width and fixed pixel font sizes, then given `width: 100%` for a responsive override, needs its container audited too.** Nested "framing" padding (an outer card's padding plus an inner preview-wrapper's own padding) compounds fast on a narrow screen and can shrink a component enough that its *un-scaled* fixed-size fonts start looking disproportionate to the box around them, even though nothing about the fonts themselves changed.
- **Never hand a real user a fabricated-looking number for anything safety-adjacent** (a dermal dilution limit, a chemical percentage, a pregnancy-safety claim) when the underlying source doesn't actually support it. Missing data should look like missing data.

## Deployment

Ship as a single static HTML file (or, if you split assets, make sure nothing critical — art, data — lives in a second file that could get separated from the first in transit). Any static host works. No server-side code is required except for a third-party form backend for the email gate, if you keep that feature.
